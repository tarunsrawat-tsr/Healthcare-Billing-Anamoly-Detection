Flags mark billing that is statistically unusual relative to peer hospitals and worth human review. They are not findings of fraud, waste or wrongdoing. CMS publishes this file as aggregate averages per provider × DRG, so a flag is a lead, never a conclusion.

Peer hierarchy usage — how each row found its comparison group

A row is compared to the finest peer group that has at least min_support members: same DRG in the same hospital referral region, else same DRG in the same state, else that DRG nationally. Falling back is normal — it means the local group was too thin to trust.

Why rows were not flagged — guard diagnostics

Every row gets exactly one reason, so these must sum to 100%. A guard that fires a lot is not a bug, it is a design decision made visible: within_peer_range should dominate.

How this works. Ingest 197,283 rows of dirty CMS CSV (money as "$1,016,806.46", comma-grouped counts, zero-padded IDs) into DuckDB with an explicit schema and a reject count → build peer statistics at three levels of a hierarchy → score each row with a robust median/MAD z plus a practical-significance floor and dispersion guards → run an Isolation Forest over case-mix-normalised features as a genuinely independent second opinion → serve the result read-only over HTTP.
  • Two detectors, two reference frames: the peer z asks "unusual among your local peers", the forest asks "unusual nationally for this DRG". They agree on a small overlap (Jaccard above) and that disagreement is the interesting result, not a defect.
  • Nothing is retrained per request and no model is pickled: the pipeline is deterministic and rebuilds in seconds, so the run manifest (input SHA-256, config, library versions, metrics, quantile profile) is the reproduction recipe.
